# Search SDK design

Status: the provider-neutral `ys::search` facade, `Policy.search`, Brave/Bing Direct HTTP adapters, DuckDuckGo browser adapter, and CLI preview are implemented in the default workspace. The built-in provider routes are versioned local previews pending certification. The [Search SDK design crate](../.local/cleanup-20261004/design-prototypes/search-sdk-zero/README.md) records the original caller and type sketches; this document describes the implemented boundary and its remaining gates.

The [project delivery plan](https://linear.app/cascadinglabs/document/yosoi-search-delivery-plan-brave-bing-duckduckgo-cli-510a4aec4578) gives the issue order, provider certification gates, CLI acceptance, and final verification for the Brave/Bing/DuckDuckGo slice.

## Ownership

Search owns query intent, provider routing, result-page classification and parsing, normalization, and per-provider outcomes. It uses the existing Yosoi Requests lifecycle, bounded Documents, Locators, and Contracts. The complete Yosoi Policy gains a Search section; there is no second HTTP stack or policy SDK. Search returns source candidates and does not automatically fetch result pages. DDGS and SearXNG code and runtimes are not used.

## One search across providers

One `SearchRequest` binds to one complete `Policy`. `Policy.search.providers` is an ordered, nonempty provider list for an enabled search. Each provider uses its versioned Current Requests profile, including acquisition, documents, and limits; an explicit Exact override can pin a complete profile in policy. Current Brave and DuckDuckGo use headless Browser Requests; Current Bing uses Direct HTTP. Their status is Preview until certification, and a missing browser capability remains a visible `NotStarted` outcome. Any number of distinct registered providers can be selected, subject to explicit concurrency, deadline, and retained-content budgets. Search dispatches provider Requests concurrently up to the policy limit and returns one provider outcome per selection in policy order. A failed or challenged provider does not turn another provider's results into failure or disappear as an empty list. Current Bing Preview v2 can make one sequential, visible content-term recovery Request after `query_mismatch`; Exact Bing routes keep their authored single-Request behavior. Both Request IDs and capture IDs remain visible, and recovered hits are marked partial. There is no cross-provider deduplication or global rank mixing.

`Policy.search.max_results_per_provider` sets the result count for each selected provider; the request currently holds bounded query intent. V0 exposes no additional search filters. `Search.max_total_results` bounds all retained hits, and preparation checks the full plan before I/O. `Search.max_retained_content_bytes` bounds retained URLs and provider text across results; JSON framing, escaping, and CLI metadata are outside that content bound. Any future filter must be validated against every selected provider before work begins. A missing runtime capability for one provider becomes that provider's visible `NotStarted` outcome while others can run; no provider silently changes acquisition. Cancellation and the absolute Search deadline preserve completed outcomes and mark unstarted providers. The deadline stops admission and cancels active Requests; `send` may return after that instant while a bounded Requests or browser cleanup grace finishes.

## Result shape

Each provider outcome carries its exact provider and configuration identity, effective acquisition, Requests attempt/capture facts, terminal classification, and known or unknown charge. The current query-only CLI reports an empty applied-filter list. Web hits have validated HTTP(S) destination URLs and provider-local organic ranks. Sponsored results, AI answers, images, and local/map panels are separate typed features; the first adapter may report that feature extraction was not performed. Provider snippets and displayed metadata are not the fetched target page's head/meta tags.

## Delivery sequence and evidence

Brave and Bing Direct HTTP adapters replay hash-checked captured pages with validated destination extraction, including Bing `/ck/a` wrappers. A bounded local live corpus produced complete positive results for both; genuine no-results and challenge pages remain uncertified. DuckDuckGo's headless regular-Stable browser route returned useful results and one observed English empty layout in the hardened container. The same container's `yosoi search` CLI returned ten complete hits from Brave, Bing, and DuckDuckGo in Policy order under a three-provider Exact preview profile. See [HTTP evidence](archive/search-local-http-evidence-2026-10-03.md), [DDG container evidence](archive/search-ddg-container-evidence-2026-10-03.md), and [Search CLI](cli-search.md). The current Brave preview uses an explicitly tested headless Browser route after Direct HTTP returned `rate_limited` in a local run. Bing stays Direct HTTP; it can return HTTP-200 organic rows about an unrelated single query term while echoing the full requested query. A detected mismatch in the Current Bing route gets one shorter content-term Request. If its page is also off-query, Bing fails with `query_mismatch`; otherwise useful recovered hits carry partial coverage and `query_relaxed`. The three provider adapters use pinned or provider-owned row locators followed by Contract field validation, then provider-specific URL and rank rules. Current routes are local previews until each provider's empty/challenge, drift, rate-state, and applicable browser-baseline gates pass. Google remains deferred.

The complete serialized Policy includes Search in effective identity v5. Archive reads preserve pre-Map v2, both Map v3 shapes, and pre-robots Search v4 identities from their authored historical shapes. Provider defaults may change between Yosoi releases: snapshot resolution records the effective acquisition/profile, Preview or
Certified status, and defaults version, and archived runs retain that resolved identity rather than applying newer defaults. Provider-specific acquisition resolution must reuse the same Requests policy vocabulary and receipts.
